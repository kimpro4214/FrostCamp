# 성능 측정과 최적화 2차 (2026-11-21)

의도: `docs/intent/frost_camp_performance.md`. 10년 된 노트북의 웹 빌드에서 렉이 걸렸다. 목표는 "하"에서 60fps이고, 그 위로도 높을수록 좋다. 이번에는 코드 구조부터 손봤다.

## 측정 방법
- 봇(시드 1)으로 22분까지 진행한 판을 저장하고 이어하기로 열었다. 일꾼 27명, 판매대 4개, 컨베이어 3줄이다.
- 측정 PC는 RTX 5060이고 1280×720, 수직 동기화를 껐다.
- 4초 동안 데운 뒤 8초를 쟀다.
- 측정 스크립트는 scratchpad에만 두었다. 측정이 끝난 뒤 사용자 저장·설정·기록 파일을 원래대로 되돌렸다.

## 어디가 무거웠나
- 노드를 초당 약 330개 새로 만들고 지웠다. 대부분 물건 상자였다.
  - **등 뒤 스택(`stack_view.gd`):** 물건 하나만 바뀌어도 쌓인 상자를 모두 지우고, 모델 GLB를 다시 불러 크기를 다시 쟀다.
  - **적치장(`woodpile_view.gd`):** 개수가 하나만 바뀌어도 상자를 모두 다시 만들었다.
  - **판매대 재고·돈 더미(`stall_view.gd`):** 같은 방식으로 다시 만들었다.
  - **손님:** 들어올 때마다 뼈대와 애니메이션이 있는 캐릭터를 통째로 새로 만들고, 나가면 지웠다.
- 그리기는 1차 기록과 비슷하다. 그리기 호출 724번, 화면 안 물체 827개이고, 그림자 패스까지 합쳐 삼각형 34만 개다.

## 바꾼 것
- **등 뒤 스택:** 아래부터 같은 물건은 그대로 두고 바뀐 칸 위만 고친다. 내려놓은 상자는 물건 이름별 풀(트리 밖)에 모아 다시 쓴다.
- **적치장과 판매대 재고·돈 더미:** 상자는 한 번 만들면 두고, 개수만큼만 보인다.
- **손님:** 떠난 손님을 풀(트리 밖, 애니메이션이 돌지 않음)에 모았다가 다음 손님으로 다시 쓴다. 들고 있던 물건만 버린다.

## 결과

| | 전 | 후 |
|---|---|---|
| 보통: fps | 334 | 377 |
| 보통: 평균 프레임 | 3.00ms | 2.65ms |
| 보통: 가장 느린 프레임 | 16.6ms | 5.0ms |
| 스크립트 처리 시간(TIME_PROCESS) | 12.9ms | 4.7ms |
| 낮음: fps | 361 | 410 |
| 낮음: 가장 느린 프레임 | 13.6ms | 6.2ms |
| 새로 만드는 노드 | 초당 약 330개 | 거의 0 (풀에서 다시 씀) |

- 가장 느린 프레임이 크게 줄었다. 웹(WASM)은 같은 CPU 일을 네이티브보다 몇 배 느리게 하므로, 오래된 노트북에서 걸리던 순간 렉이 이 몫이었을 가능성이 크다.
- 그리기 호출과 삼각형 수는 그대로다. 모습이 바뀌지 않는 수정이라서다.
- 봇 엔딩은 29.4, 28.4, 27.8, 26.4, 26.2분으로 바꾸기 전과 같다. 규칙은 그대로다.
- 테스트 148개가 모두 통과했다.

## 재 봤지만 고치지 않은 것
- 갈래별로 process를 꺼서 스크립트 시간을 나눠 보려 했다. 하지만 이 PC에서는 측정 흔들림(±2ms)이 차이보다 커서 원인을 가를 수 없었다.
- 날아가는 동전(초당 약 4개)과 떠오르는 숫자 Label3D(초당 약 2개)는 양이 적어 그대로 두었다.

## 그리기 호출 줄이기 (같은 날 이어서)
- **물건 그림자 끄기:** `item_model.gd`가 만드는 물건(등 뒤 스택, 동전, 컨베이어 위 물건, 손님이 든 물건, 낚은 연어)은 그림자를 그리지 않는다. 작아서 그림자가 거의 안 보이는데, 그림자 패스에서 하나씩 다시 그려졌다.
- **MultiMesh:** 적치장 상자와 판매대 재고·돈 더미를 `item_multi.gd`로 묶었다. 물건 모델의 메시마다 MultiMesh 하나를 두고, 자리는 처음에 정하고 보일 개수만 바꾼다.

| | 풀 적용 뒤 | + 그림자 끄기 | + MultiMesh |
|---|---|---|---|
| 보통: 그리기 호출 | 724 | 574 | 552 |
| 보통: 화면 안 물체 | 827 | 678 | 657 |
| 보통: fps | 377 | 374 | 370~392 |
| 낮음: 그리기 호출 | 491 | 407 | 385 |
| 낮음: fps | 410 | 394 | 384 |

- 그리기 호출이 보통 24%, 낮음 22% 줄었다(724 → 552, 491 → 385).
- 이 PC는 그래픽 카드가 빨라 fps 차이가 측정 흔들림 안에 든다. 그리기 호출은 웹(WebGL)과 약한 내장 그래픽에서 더 비싸므로, 오래된 노트북에서 재야 효과가 보인다.
- MultiMesh 효과가 작은 건, 한 화면에 보이는 적치장·판매대가 몇 개뿐이어서다.
- 화면으로 적치장 원목, 판매대 원목·연어 재고, 손님이 든 물건이 전과 같은 자리에 보이는 것을 확인했다.
- 한 번 91ms 프레임이 나왔지만, 두 번 다시 재니 나오지 않았다(처음 셰이더를 만들 때로 본다).

## 다음
- 그리기 쪽에서 가장 큰 남은 몫은 기본 도형으로 만든 사냥 곰이다. 화면 안 메시가 98개이고, 그림자 패스로 다시 그린다. 사용자가 만들 곰 메시(몸통 하나 + 다리 4개)로 바꾸면 곰 하나에 그리기 호출이 약 19번에서 5번으로 준다.
- 캐릭터 삼각형(약 1만 개짜리)은 그래픽 "하"에서 사용자가 만든 약 3천 개짜리 메시로 바꾼다. 의도 문서의 2단계다.
- 실제 10년 된 노트북의 웹 빌드에서 다시 재야 60fps 여부를 알 수 있다.
